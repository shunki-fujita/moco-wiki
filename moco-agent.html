moco-agent — mysqld Pod のサイドカー

別リポジトリ cybozu-go/moco-agent（v0.16.0）。MySQL の初期化、readiness/liveness probe、CLONE の gRPC API、slow log ローテーションを担当します。scratch ベースのイメージに 3 つのバイナリが同梱されています。

3 つのバイナリ

バイナリ役割
/moco-agentサイドカー本体。初期化 + gRPC (:9080) + probe (:9081) + metrics (:8080) + ログローテ
/moco-initinit コンテナで実行。データディレクトリ初期化（mysqld --initialize-insecure）と instance 固有 my.cnf（server_id と admin_address の 2 行だけ）の生成。server_id = serverIDBase + Pod index
/bin/cpscratch イメージに cp が無いための自前実装。init コンテナ copy-moco-init が moco-init を emptyDir へコピーするのに使う

moco-init は初期化済み判定に <data-dir>/moco-initialized マーカーを使い、作成時は書き込み → syncfs → rename → ディレクトリ sync という耐障害手順を踏みますcmd/moco-init/main.go#initMySQL。

起動シーケンス

  1. POD_NAME / AGENT_PASSWORD / CLUSTER_NAME を確認（無ければ即終了）
  2. MySQL 初期化を同期実行（下記）。終わるまでサーバは立たない
  3. mysqld の admin ポート (33062) への TCP 接続プールを作成 — mysqld が起動していないと agent は起動失敗
  4. cron（ログローテ）、gRPC サーバ（mTLS）、probe HTTP、metrics HTTP を起動。証明書は 1 時間ごとにリロード

cmd/moco-agent/cmd/root.go#RunE

MySQL 初期化

UNIX ソケット経由でパスワード無し root@localhost として接続を試み、接続できなければ「初期化済み」と判断して何もしない（エラー 1045/1524 を「root がもういない」と解釈）。これが Pod 再起動時の冪等性の要ですserver/connect.go#UserNotExists。

接続できた場合の初期化フローserver/initialize.go#Init:

read_only=OFF
→ ユーザ 8 種を作成 (partial_revokes=ON)
→ プラグイン導入 (rpl_semi_sync_master / rpl_semi_sync_slave / clone)
→ moco-admin で再接続し root@localhost を DROP
→ RESET MASTER (8.4 では RESET BINARY LOGS AND GTIDS)   ← GTID を空にする
→ super_read_only=ON
RESET MASTER で GTID set を空にするのが重要ポイント。MOCO 本体は「gtid_executed が空」を「CLONE してよい空インスタンス」の判定に使っています。

作成される MySQL ユーザと権限

ユーザ権限（要約）
moco-adminALL WITH GRANT OPTION + GRANT PROXY。controller の操作用
moco-agentBINLOG_ADMIN, CLONE_ADMIN, RELOAD, REPLICATION CLIENT, SELECT, SERVICE_CONNECTION_ADMIN, SYSTEM_VARIABLES_ADMIN
moco-replREPLICATION CLIENT, REPLICATION SLAVE
moco-clone-donorBACKUP_ADMIN, SERVICE_CONNECTION_ADMIN（クローンのドナー側）
moco-exporterPROCESS, REPLICATION CLIENT, SELECT
moco-backupBACKUP_ADMIN, EVENT, RELOAD, SELECT, SHOW VIEW, TRIGGER, REPLICATION CLIENT/SLAVE, SERVICE_CONNECTION_ADMIN
moco-readonlyPROCESS, REPLICATION CLIENT/SLAVE, SELECT, SHOW DATABASES, SHOW VIEW（エンドユーザ読み取り用）
moco-writableCREATE/ALTER/DROP/INSERT/UPDATE/DELETE 等 24 権限 WITH GRANT OPTION。ただし mysql.* への書き換え系 14 権限は partial revoke で剥奪（システムスキーマを壊せない）

ホストはすべて '%'。パスワードは 8 つの環境変数（ADMIN_PASSWORD, AGENT_PASSWORD, REPLICATION_PASSWORD, CLONE_DONOR_PASSWORD, EXPORTER_PASSWORD, BACKUP_PASSWORD, READONLY_PASSWORD, WRITABLE_PASSWORD）から取得し、Secret の envFrom で注入されます。

既存ユーザに対しては何もしない（reset=false）ため、Secret のパスワードを変えても既存インスタンスには自動反映されません。パスワードが上書きされるのはクローン直後の InitExternal（donor 側のパスワードが混入するため reset=true で強制上書き）だけです。

gRPC API — メソッドは Clone のみ

サービス moco.Agent のメソッドは /moco.Agent/Clone の 1 つだけです。CloneRequest は donor の host/port/user/password、クローン後初期化用の init_user/init_password、boot_timeout を持ちますproto/agentrpc.proto。

  1. 排他ロック（同時実行は ResourceExhausted）
  2. Executed_Gtid_Set が空でなければ FailedPrecondition "recipient is not empty" — データのあるインスタンスを誤って潰さないガード
  3. clone_valid_donor_list を設定し、タイムアウトを付けない UNIX ソケット接続で CLONE INSTANCE FROM ... を実行
  4. MySQL エラー 3707（クローン後の自動再起動で接続断）は成功扱い
  5. mysqld の再起動を待って（既定上限 10 分）、InitExternal でユーザのパスワード上書きとプラグイン確認。gRPC がキャンセルされても context.Background() で完遂する

Clone は レプリケーションを開始しません。START REPLICA は MOCO 本体（configure）の責務です。

mTLS

/grpc-cert に ca.crt / tls.crt / tls.key が必要。RequireAndVerifyClientCert に加えて、クライアント証明書の CN が文字列 moco-controller と完全一致しないと拒否します。cert-manager のローテーションには 1 時間ごとの再読込で追随cert/cert.go#verifyConnection。

probe の実装

probe HTTP (:9081) は agent が提供しますが、MOCO は これを mysqld コンテナの probe として設定します（Pod 内でネットワーク namespace を共有しているため届く）。

エンドポイント判定
/healthz
(startup / liveness)		admin ポートで SELECT VERSION() が通るかだけ。遅延や read_only は見ない
/readyz
(readiness)		順に: ① クローン進行中なら 503 → ② read_only=false（= primary）なら即 200 → ③ レプリケーションスレッド停止/エラーなら 503 → ④ 遅延判定（下記）

遅延は Seconds_Behind_Source ではなく、performance_schema から取った「受信済み最新トランザクションのコミット時刻 − 適用済み最新トランザクションのコミット時刻」で計測します（lag = queued − applied）。--max-delay（MySQLCluster の maxDelaySeconds、既定 60s）以上なら 503。起動直後でまだトランザクションを受信していない場合は「遅延 0」と誤判定せず、--transaction-queueing-wait（既定 1m）の間は 503 を返しますserver/mysqld_health.go#MySQLDReady。

probe が mysqld コンテナに設定されているため、moco-agent が落ちると mysqld コンテナの liveness が失敗して mysqld が再起動されます。また Pod の Ready = /readyz の判定そのものであり、primary/replica Service のエンドポイント登録に直結します。

ログローテーション

対象は slow query log のみ（/var/log/mysql/mysql.slow）。cron（既定 5 分ごと、logRotationSchedule で変更可）で mysql.slow → mysql.slow.0 に rename して FLUSH LOCAL SLOW LOGS。保持は 1 世代のみ（.0 は毎回上書き）。logRotationSize > 0 なら 1 秒ごとのサイズ監視でも発火しますserver/rotate.go#RotateLog。ローテート後のファイルは同じ volume を読む fluent-bit（slow-log サイドカー）が転送します。

MySQL への接続の使い分け

接続用途
TCP :33062 (admin port)常設プール（moco-agent ユーザ）。probe・ローテーション用。admin 接続は専用スレッドで処理されるため max_connections 枯渇時でも probe が通る。ReadTimeout 30s
UNIX ソケット /run/mysqld.sock初期化（root → moco-admin）と CLONE 実行。タイムアウト無し（長時間クローン対応）。TCP リスナー未起動の初期化フェーズでも使える

メトリクス（moco_instance_*）

ラベルは name（クラスタ名）と index（Pod index）。replication_delay_seconds（readiness 判定時に更新）、clone_count / clone_failure_count / clone_duration_seconds / clone_in_progress、log_rotation_count / log_rotation_failure_count / log_rotation_duration_seconds。加えて gRPC サーバメトリクス（grpc_server_*）と Go runtime メトリクスが同じ /metrics (:8080) に出ます。

ソースから見つかった注意点（docs との食い違い）

  • docs/moco-agent.md の環境変数表に EXPORTER_PASSWORD / BACKUP_PASSWORD が抜けている（実装は 8 個すべて必須）
  • docs のフラグ一覧に --mysqld-localhost が無く、逆に実装に存在しない --logfile / --logformat / --loglevel が載っている（現在は zap 固定）
  • moco_instance_replication_delay_seconds は動的に登録/解除されるため、primary やトランザクション未受信のレプリカではメトリクス自体が存在しない
  • moco_instance_log_rotation_count だけ name / index ラベルが付かない（ConstLabels の指定漏れ）
  • slow log の保持は 1 世代のみ。fluent-bit が読み終える前に次のローテートが来ると欠損しうる
