Internals

Pod の構成と my.cnf の生成

mysqld Pod がどう組み立てられ、my.cnf がどんな規則で生成されるか。ユーザが上書きできる設定とできない設定の境界をまとめます。

Pod の解剖図

initContainers:
  copy-moco-init    agent イメージ。 cp /moco-init /shared/moco-init
  moco-init         mysqld イメージ。データディレクトリ初期化 +
                    server_id / admin_address を /etc/mysql-conf.d に生成
  (ユーザ定義 initContainers)

containers:
  mysqld            ユーザ指定イメージ。--defaults-file=/etc/mysql/my.cnf
  agent             moco-agent。gRPC :9080 / metrics :8080
  slow-log          fluent-bit (disableSlowQueryLogContainer=false のとき)
  mysqld-exporter   spec.collectors 非空のとき (:9104)
  (ユーザ定義コンテナ)

moco-init が mysqld イメージで動くのは mysqld --initialize-insecure を実行するため。moco-agent のバイナリを mysqld イメージに焼き込まない設計ですcontrollers/mysql_container.go#makeV1InitContainer。

mysqld コンテナの probe と終了処理

設定値備考
startupProbeGET /healthz :9081、period 10s × failureThreshold max(startupWaitSeconds/10, 1)既定 3600s → 最大 1 時間待つ。MySQL バージョンアップ時のデータ更新を見込んだ値
livenessProbeGET /healthz :9081応答するのは moco-agent（同一 Pod の network namespace）
readinessProbeGET /readyz :9081レプリカ遅延も判定（moco-agent 参照）
preStopsleep 20Service のエンドポイント除去が伝播するまでの猶予。switchover のタイムアウト（10s）はこの半分
terminationGracePeriodSeconds300（未指定時）

サイドカーのリソース既定値

コンテナCPU (req=limit)Memory (req=limit)
agent100m100Mi
copy-moco-init / moco-init100m512Mi
slow-log (fluent-bit)100m20Mi
mysqld-exporter200m100Mi

mysqld 本体のリソースには既定値がなく、ユーザが podTemplate で指定します（limits のみ指定して Guaranteed QoS にするのが docs の推奨例）。サイドカーの resources / securityContext は spec.podTemplate.overwriteContainers で上書きできます。

securityContext は全コンテナに runAsUser/runAsGroup=10000、Pod に fsGroup=10000 + fsGroupChangePolicy=OnRootMismatch が（未指定時のみ）設定されます。--disable-default-security-context で無効化可pkg/constants/container.go。

docs/customize-system-container.md には「runAsUser=1000」と書かれていますが、実装は 10000 です（ドキュメントの誤り）。

my.cnf の生成

my.cnf は「MOCO の強制設定」「デフォルト値」「ユーザ ConfigMap」の 3 層をマージして生成されます。優先順位は 強制設定 > ユーザ設定 > デフォルト ですpkg/mycnf/generator.go#Generate。

ユーザが上書きできない設定（ConstMycnf）

port=3306  socket=/run/mysqld.sock  datadir=/var/lib/mysql/data
admin_port=33062  mysqlx_port=33060
enforce_gtid_consistency=ON  gtid_mode=ON  binlog_format=ROW
log_replica_updates=ON  relay_log_recovery=OFF
read_only=ON  super_read_only=ON  skip_replica_start=ON   ← 起動時は常に read-only。
                                                             primary 化は clustering の仕事
skip_name_resolve=ON  secure_file_priv=NULL
slow_query_log_file=/var/log/mysql/mysql.slow
loose_replication_optimize_for_static_plugin_config=ON
loose_replication_sender_observe_commit_only=OFF   ← ON だとクラッシュ復帰 replica が再開不能 (issue #325)

さらに log_bin / log_error / skip_log_bin / disable_log_bin はユーザ設定から強制削除されます。

ユーザ ConfigMap とのマージ規則

  1. キー名は - → _ に正規化される（thread-cache-size と書いてもよい）
  2. loose_ prefix の有無は同一キーとして扱われる — innodb_numa_interleave: OFF と書くと既定の loose_innodb_numa_interleave: ON が置き換わる
  3. 未知のキーは検証されずそのまま出力される（typo に注意）
  4. 複数回指定が必要なオプション（performance-schema-instrument 等）は特殊キー _include に生テキストで書く。中身は無検査なので log_bin 等を壊すこともできてしまう
  5. 末尾に必ず !includedir /etc/mysql-conf.d が付き、moco-init が生成した server_id / admin_address を読み込む
# 使い方: ConfigMap を作って spec.mysqlConfigMapName で参照
apiVersion: v1
kind: ConfigMap
metadata:
  name: mycnf
data:
  long_query_time: "5"
  innodb_buffer_pool_size: "10G"
my.cnf の内容を変えると ConfigMap が新しいハッシュ名で作り直され、StatefulSet の参照が変わって mysqld のローリング再起動が走ります。設定変更 = 再起動、と覚えておくこと。
