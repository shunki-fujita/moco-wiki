Reconcile の仕組み

MySQLClusterReconciler は Server-Side Apply（field manager moco-controller）で子リソースを管理し、StatefulSet の更新は専用の webhook + Reconciler の組で「partition を 1 つずつ下げる」安全なローリングアップデートに変換されます。

リソース要点

headless ServicepublishNotReadyAddresses=true。primary / replica Service は moco.cybozu.com/role ラベルセレクタで振り分け

Server-Side Apply と差分抑制

すべての子リソースは apply configuration で宣言し、client.FieldOwner("moco-controller") + ForceOwnership の SSA で適用します。適用前に現在値から自分の所有フィールドを extract して期待値と比較し、等価なら apply 自体をスキップします（ErrApplyConfigurationNotChanged）。これで resourceVersion の無駄な更新と reconcile ループの自己発火を防いでいますmysqlcluster_controller.go#apply。

安全なローリングアップデート（partition 制御）

MySQLCluster 所有の StatefulSet に対して mutating webhook（/mutate-apps-v1-statefulset）が介入しますapi/v1beta2/statefulset_webhhok.go:

  1. spec 変更時、rollingUpdate.partition = replicas にセット（= 全 Pod の更新を止めた状態から開始）
  2. StatefulSetPartitionReconciler が「クラスタが Healthy かつ Pod が rollout-ready」のときだけ partition を 1 つずつ下げる
  3. partition だけの変更はそのまま通す。他の spec 変更が同時に入ると partition をリセットして最初からやり直し
  4. 更新は ordinal の大きい Pod（= replica）から進み、primary Pod の番になると Terminating を検知した ClusterManager が switchover してから更新が進む
sequenceDiagram
    participant U as ユーザ / MOCO
    participant W as StatefulSet webhook
    participant P as PartitionReconciler
    participant S as StatefulSet
    U->>S: spec 変更 (イメージ更新等)
    W->>S: partition = replicas に設定 (更新を全停止)
    loop クラスタが Healthy の間
        P->>S: partition を 1 下げる
        S->>S: 最大 ordinal の未更新 Pod を再作成
        Note over S: primary の番になったら
switchover してから続行
    end

moco.cybozu.com/force-rolling-update: "true" アノテーションでこの機構をバイパスし、通常のローリングアップデートに戻せます。

Reconciler バージョニング

status.reconcileInfo.reconcileVersion を見て、既存 generation には古いバージョンの reconcile ロジックを使い続けます。これにより MOCO 自体の更新では mysqld Pod が再起動しません（spec を変更したときに初めて新ロジックが適用される）mysqlcluster_controller.go#Reconcile, docs/reconcile.md。
