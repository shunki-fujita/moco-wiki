Internals

クラスタリングと failover

MOCO は状態機械を「保存」しません。ClusterManager が毎サイクル全インスタンスの状態を集めて状態を再計算し、状態に応じた操作を実行する level-triggered な設計です。

維持ループ

ClusterManager は MySQLCluster ごとに goroutine（managerProcess）を 1 本起動し、--check-interval（既定 1 分）ごと、またはイベント（Pod 変化、reconcile 完了）を契機に 1 サイクルを回します。操作を行った場合は redo として即座に次サイクルが走りますclustering/manager.go, process.go#Start。

do():  GatherStatus       全 mysqld から並列に状態収集（失敗は 3 秒間隔で最大 3 回試行）
       DecideState        クラスタ状態を判定
       updateStatus       status / conditions / メトリクス更新
       PreventPodDeletion レプリカ遅延超過なら primary に prevent-delete アノテーション
       操作               状態に応じて switchover / failover / configure / clone

clustering/process.go#do

収集する情報

各 mysqld の admin ポート (33062) に接続し、グローバル変数（server_uuid, gtid_executed, gtid_purged, read_only, super_read_only, semi-sync 変数）、SHOW REPLICAS / SHOW REPLICA STATUS、performance_schema.clone_status、Rpl_semi_sync_master_wait_sessions を取得します。primary は 100ms 待って再取得し、その gtid_executed を基準値にしますclustering/status.go#GatherStatus, pkg/dbop/status.go。

8 つのクラスタ状態

状態意味実行される操作
Healthy全 Pod Ready、全レプリカが errant なし・super_read_only・primary に接続済み、SHOW REPLICAS のクラスタ内レプリカ数が replicas−1 に完全一致必要なら switchover
Cloning外部 MySQL からの初回 CLONE 中（intermediate primary）clone 実行 / 完了待ち
Restoringバックアップからのリストア中何もしない
Degradedprimary は書き込み可能だが一部レプリカに問題（半数以上は正常）switchover または configure
Failedprimary 死亡 or データ喪失 + 正常レプリカが過半数failover
Lostprimary 死亡 + 正常レプリカが半数以下。自動復旧不能何もできない（リストアが必要）
Incomplete上記以外（初期構築中など）configure
Offlinespec.offline: true。判定は最優先何もしない

clustering/status.go#DecideState（判定順: Offline → Cloning → Restoring → Healthy → Degraded → Failed → Lost → Incomplete）。Offline 状態は docs/clustering.md には未記載（コードのみ）

状態遷移

stateDiagram-v2
    [*] --> Cloning: replicationSourceSecretName あり
    [*] --> Restoring: spec.restore あり
    [*] --> Incomplete: それ以外

    Cloning --> Incomplete: CLONE 完了
    Restoring --> Incomplete: restoredTime セット

    Incomplete --> Healthy: configure() 成功
    Incomplete --> Degraded: 半数以上のレプリカが正常

    Healthy --> Healthy: switchover (primary が Terminating / demote)
    Healthy --> Degraded: レプリカ障害 / errant / hangup 検出
    Healthy --> Failed: primary ダウン + 正常レプリカ > replicas/2
    Healthy --> Lost: primary ダウン + 正常レプリカ <= replicas/2

    Degraded --> Healthy: configure() で全レプリカ復旧
    Degraded --> Failed: primary ダウン + 過半数正常
    Degraded --> Lost: primary ダウン + 半数以下
    Degraded --> Incomplete: 正常レプリカが replicas/2 未満

    Failed --> Degraded: failover 成功 (一部未復旧)
    Failed --> Healthy: failover + 全レプリカ復旧
    Failed --> Lost: さらにレプリカ喪失

    Lost --> [*]: バックアップから復元するしかない

遷移条件の根拠: clustering/status.go の isHealthy / isDegraded / isFailed / isLost。replicas/2 は整数除算（replicas=3 → 1, replicas=5 → 2）。primary 死亡時は必ず Failed か Lost のどちらかになる

switchover — 計画的な primary 交代

primary Pod に deletionTimestamp が付く（ローリングアップデート等）か、moco.cybozu.com/demote: true アノテーションが付くとトリガーされます。候補は「正常なレプリカのうち最小 ordinal」status.go#needSwitch, #DecideState。

  1. primary を super_read_only=1 に。10 秒（preStop 20 秒の半分）で終わらなければ接続を KILL して待ち直す
  2. 100ms 後にもう一度接続を KILL
  3. 候補レプリカが primary の GTID に追いつくのを最大 50 秒待つ（WaitForGTID）
  4. status.currentPrimaryIndex を更新（次サイクルの configure で新 primary が書き込み可能になる）。demote アノテーションを削除

clustering/operations.go#switchover

failover — 障害時の primary 昇格

  1. 全レプリカの IO_THREAD を停止 — 旧 primary が semi-sync ACK を得られなくなり書き込み不能になる（split-brain 防止）
  2. errant でないレプリカから GTID_SUBSET の包含比較で最も GTID が進んだものを選出（FindTopRunner）。Retrieved_Gtid_Set と Executed_Gtid_Set の和集合で比較する（failover 直後で Retrieved が空のケースに備える）
  3. Retrieved_Gtid_Set の適用完了を最大 50 秒待ち、currentPrimaryIndex を更新
switchover は「最小 ordinal」、failover は「最も進んだ GTID」と選出基準が異なります。failover は DecideState が選んだ候補を FindTopRunner の結果で上書きしますoperations.go#failover, pkg/dbop/gtid.go#FindTopRunner。

configure — Degraded / Incomplete からの復旧

冪等な復旧処理です。実行順:

  1. 役割が変わった Pod（errant 含む）から moco.cybozu.com/role ラベルを剥がす — ユーザトラフィックを Service から外す
  2. 300ms（MOCO_ROLE_WAIT_DURATION で変更可）待って、該当インスタンスの接続を KILL
  3. primary の設定: semi-sync primary を有効化。intermediate primary の場合は super_read_only のまま外部ソースへ非 semi-sync でレプリケーション開始
  4. 各レプリカを構成（下記）
  5. 役割ラベルを付け直す（errant には付けない）
  6. primary を書き込み可能に（read_only=0）、Event Writable を発行

configureReplica の要点

  • CLONE の実行条件: レプリカの gtid_executed が空 ∧ primary の gtid_executed が非空 ∧ ReplicaStatus が nil、の 3 条件 AND。moco-agent 経由で primary から CLONE INSTANCE し、再起動を最大 60 秒待つ
  • binlog 欠損の防御: GTID_SUBTRACT(primary の gtid_purged, レプリカの gtid_executed) が非空なら「必要な binlog が primary に無い」としてエラーで中断
  • errant レプリカは IO_THREAD を止めるだけで再開しない（隔離）

clustering/operations.go#configure, #configureReplica, #configurePrimary

semi-sync と errant transaction

設定 / 挙動値・内容
rpl_semi_sync_master_timeout24 時間（86400000 ms）— 非同期への劣化を事実上禁止
rpl_semi_sync_master_wait_for_slave_countreplicas / 2（5 台なら 2）。replicas=1 では semi-sync 設定なし
レプリケーション構文GTID ベース（SOURCE_AUTO_POSITION=1）。MySQL 8.4 は CHANGE REPLICATION SOURCE TO、8.0 は CHANGE MASTER TO に自動切替
errant 検出primary 上で GTID_SUBTRACT(replicaGTID, primaryGTID) を評価し、差分に primary 以外の UUID があれば errant。primary 自身の UUID の差分は無視（高負荷時にレプリカの gtid_executed が一時的に先行することがあるため）。primary ダウン中は status.errantReplicaList から復元
errant レプリカの扱いレプリケーション停止のまま隔離。role ラベルを剥がして Service から外し、failover 候補からも除外。復旧はユーザが PVC + Pod を削除して再初期化
hangup 検出レプリカ側で Rpl_semi_sync_master_wait_sessions > 0（レプリカが ACK 待ちしている異常）ならそのレプリカを死亡扱いに → Healthy から Degraded に落ちる

pkg/dbop/replication.go, clustering/status.go#containErrantTransactions

落とし穴

  • Pod が 1 つでも欠けると GatherStatus がエラーで打ち切られ、判定も操作も行われない（offline 時を除く）status.go#GatherStatus
  • spec.offline は最優先判定 — Failed 状態でも offline にすれば failover は走らない
  • maxDelaySecondsForPodDeletion 超過中は primary に moco.cybozu.com/prevent-delete が付き、switchover も保留される
  • switchover のタイムアウトは 10 秒固定（preStop 20 秒 ÷ 2）。超えると failover 経路に落ちうる
  • mysqld への接続は connTimeout 5s / readTimeout 1m。落ちたインスタンスがあると 1 サイクルに 3 秒 × 3 回のリトライ分の待ちが入る
